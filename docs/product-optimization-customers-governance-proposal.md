## 当前判断

- 现有客户页方向其实已经比传统大卡片列表更对：
  - 已经有 `顶部指标 + 客户切片 + 主表格 + 右侧详情栏`
  - 也已经有 `今日待跟进 / 高意向 / 报价未回 / 已停滞 / 需排日程`
  - 右侧也已经具备 `记录互动 / 加入日程 / 发起报价 / 打开详情`

- 所以客户页这次不建议推倒重来。
- 更适合的做法是：
  - 保留现有“高密度 CRM 工作台”骨架
  - 把重点从“推荐式浏览”进一步推进到“治理式处理”

## 当前问题

### 1. 机会看到了，但治理动作还不够集中

- 当前更擅长找“值得推进的客户”。
- 但还不够擅长找：
  - 资料不完整的客户
  - 疑似重复客户
  - 负责人已到期待维护的客户
  - 应该先补日程还是先补资料的客户

### 2. 客户池治理目标还没真正进入主界面

- 现在 P1 的目标里已经明确有：
  - 去重
  - 合并
  - 超时跟进
  - 负责人负载
- 但正式客户页主界面里，目前真正直观可处理的，主要还是跟进机会。

### 3. 行操作仍偏“跳转型”，还不够“处置型”

- 当前表格里的行内操作以：
  - `详情`
  - `记互动`
  为主。
- 这适合查阅，但还不够像真正的“客户池治理台”。

### 4. 去重和负载目前更适合先做轻版，不适合一次做重

- 当前代码里已有负责人保护、认领、审批等能力。
- 但没有现成的“客户合并”正式能力。
- 所以这轮不建议直接做重型合并流。
- 更稳妥的是先上：
  - `疑似重复提醒`
  - `负责人待维护提醒`
  - `轻量负载盘点`

## 方案目标

- 让客户页从“能看”升级成“能治理”。
- 这版核心不是做更花的视觉，而是让业务和管理者能更快回答这几个问题：
  - 今天先跟进谁
  - 哪些客户资料不完整
  - 哪些报价已经失温
  - 哪些客户可能重复
  - 哪些负责人已经压住太多待推进客户

## 建议方案 V1

### 一、页面骨架不推翻，继续保留现在的三段式

- 保留：
  - 顶部概览
  - 中部切片 + 主表格
  - 右侧固定处理栏

- 原因：
  - 这套骨架已经符合 CRM 的高频使用方式
  - 不需要再回到“大卡片叙事式”结构
  - 重点应该放在队列定义和字段表达

### 二、把“客户切片”升级为真正的治理队列

- 当前切片建议从偏机会视角，升级成“机会 + 治理”混合队列。

### 建议保留

- `今日待跟进`
- `报价未回`
- `需排日程`

### 建议新增

- `待补资料`
  - 用来收口缺企业名称 / 缺联系人 / 缺下一步动作的客户

- `可能重复`
  - 第一版只做提醒，不做自动合并
  - 可先基于：
    - 手机号相同
    - 客户名相同
    - 企业名 + 联系人高度相似

- `待维护归属`
  - 基于现有 `ownerProtectionStatus === PENDING_MAINTENANCE`
  - 让负责人保护期问题不再埋在详情页

### 三、主表格增加“治理提示”，而不是只显示状态

- 当前主表格已经有：
  - 阶段
  - 负责人
  - 最近互动
  - 下一步
  - 意向
  - 报价

- 建议 V1 不大改列结构，只加轻量提示层：
  - `资料待补` 小标签
  - `疑似重复` 小标签
  - `待维护` 小标签

- 这样做的好处：
  - 不会打断当前表格密度
  - 也不会把页面重新做成说明板
  - 业务可以一眼看见“这条记录是要推进，还是要治理”

### 四、右侧详情栏改成“当前处置面板”

- 当前右侧方向是对的，建议继续保留。
- 但文案和信息顺序可以更偏“处置”：

### 建议优先展示

- 当前为什么被筛出来
- 最近一次互动时间
- 下一步动作
- 报价 / 跟进次数
- 缺失资料
- 是否待维护
- 是否疑似重复

### 建议保留动作

- `记录互动`
- `加入日程`
- `发起报价`
- `打开详情`

### 可补一个轻量动作

- `复制客户信息`
  - 便于业务快速发给同事确认
  - 这个可以后看复杂度决定是否放进第一版

### 五、负责人负载先做轻版盘点，不先上复杂分配

- 负责人负载是客户池治理的重要部分，但不建议这轮直接做调度系统。

### 第一版建议

- 先在顶部或右侧增加轻量统计：
  - 当前待推进客户最多的负责人
  - 报价未回压单最多的负责人
  - 待维护客户最多的负责人

- 价值：
  - 管理者可以先看分布是否失衡
  - 不急着把“转移负责人”也一起做进去

### 六、真正的“客户合并”放到 V2

- 这一轮不建议直接做：
  - 合并主客户
  - 合并历史跟进
  - 合并报价 / 合同 / 日程归属

- 原因：
  - 这是高风险动作
  - 一旦处理不好，会影响报价、订单、档案回链

- 所以建议节奏：
  - `V1`：先发现问题
  - `V2`：再处理真正合并

2. 测试页确认后，再把同样结构接回正式页

## 计划中的验收方式

- 看客户页时，应该能在 10 秒内回答：
  - 今天先跟进谁
  - 哪些客户资料不全
  - 哪些报价最危险
  - 哪些记录可能重复

- 页面确认标准：
  - 仍然是高密度工作台，不变成说明页
  - 不增加重叠弹层
  - 不破坏当前搜索、筛选、右侧详情的使用节奏
  - 业务对象和治理对象能放在同一张表里看清楚

## 暂不进入本轮的内容

- 客户正式合并流
- 负责人转移审批流重做
- 客户详情页大改版
- 批量认领 / 批量分配

## 当前建议结论

- 客户页下一步不建议做“重新设计一整页”。
- 更建议做成：
  - `现有正式页骨架保留`
  - `治理队列增强`
  - `表格治理提示增强`
  - `右侧处置面板增强`

- 这是风险最低、收益最高、也最容易连续推进的一版。
