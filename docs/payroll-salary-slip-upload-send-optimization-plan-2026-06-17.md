# 薪资条上传与发送优化修复方案（2026-06-17）

## 背景

本次检查目标是验证“发送薪资条”功能，重点确认此前 UI 缺少“上传档案 / 上传薪资表”入口的问题是否已修复。

当前结论：

- 薪资批量页已出现“去导入中心”“上传薪资表后返回核对”等引导文案，但页面本身没有直接上传控件。
- 实际上传入口位于财务文件导入中心 `/finance/imports`，文件类型选项包含“薪资表”，支持 `.xlsx`、`.xls`、`.csv`。
- 当前薪资前端代码位于静态压缩发布包 `apps/web/public/employee-frontend/releases/20260616090241`，未定位到可维护 Vite 源码；后续修改应先恢复或确认源代码，不建议直接修改压缩发布包。
- 本机隔离 MySQL 后端演练已完成：migration、只读 DB 验收、UAT API execute 和审计包均已通过。
- 生产 schema migration `20260617110000_payroll_publish_batch_identity` 已完成，字段和索引验收通过；历史旧薪资条和旧通知记录的 `publishBatchId / 身份字段` 已完成只读 dry-run，但真实回填仍需人工复核和单独授权。
- 前端真实登录、上传入口 UI 和上传后返回闭环仍等待员工端 Vite 源码恢复。

## 修复目标

1. 让财务在薪资批量页一眼能找到“上传薪资表”入口。
2. 上传后自动回到对应月份的薪资批量核对页。
3. 发布前强制完成原表核对、差异确认、通知名单确认。
4. 薪资条同步、企业微信通知、员工本人查看三段状态清晰可追溯。
5. 补齐自动化回归，避免以后入口再次丢失。

## 优先级总览

| 优先级 | 项目 | 目标 |
| --- | --- | --- |
| P0 | 薪资批量页直接上传入口 | 补上最关键 UI 入口，避免用户找不到上传档案 |
| P0 | 导入中心深链与返回 | 从薪资页进入时自动选“薪资表”和月份，上传后回到核对页 |
| P0 | 发布前确认摘要 | 发布前确认收件人、系统内查看人员、不发送人员和金额 |
| P1 | 后端薪资查询优化 | 本人薪资条按明确身份字段查询，不再全表读取后内存过滤 |
| P1 | 权限收紧 | 薪资维护只使用明确角色 / 权限，不再依赖文本正则 |

## 工作线 A：前端上传入口与导入体验

### A1. 薪资批量页增加主入口

在 `/payroll/batch` 顶部或空状态区域加入明确入口：

- 主按钮：`上传薪资表`
- 次按钮：`进入财务导入中心`
- 空状态说明：当前月份没有薪资导入草稿时，直接提示上传薪资表。

推荐跳转：

```text
/finance/imports?type=salary_slip&month=YYYY-MM&returnTo=/payroll/batch
```

验收标准：

- 财务进入薪资批量页后，不需要理解“导入中心”概念也能开始上传。
- 当前月份没有草稿时，上传入口仍然可见。
- 入口在桌面和手机视图都可见。

### A2. 导入中心支持薪资深链预填

当 URL 带入 `type=salary_slip` 或等价参数时：

- 上传类型默认选中“薪资表”。
- 月份默认使用 URL 传入月份。
- 文件选择区文案切换为“上传薪资表”。
- 提交成功后显示“回到薪资批量核对”。

验收标准：

- 从 `/payroll/batch` 进入 `/finance/imports` 后，类型不再默认成其他财务文件。
- 上传后不会让用户停在导入中心迷路。

### A3. 文件格式提示

导入中心当前接受 `.xlsx`、`.xls`、`.csv`，但 `.xls` 不能浏览器预览。需要在 UI 上明确：

- `.xlsx/.csv`：支持上传前预览。
- `.xls`：可上传复核，但不能在浏览器预览，建议另存为 `.xlsx`。

验收标准：

- 用户选择 `.xls` 时，看到明确非错误提示。
- 用户选择非支持格式时，看到明确拦截信息。

### A4. 导入预览与字段映射提示

薪资表预览应展示：

- 姓名 / 企业微信账号 / 部门 / 岗位
- 应发 / 提成 / 分润 / 扣款 / 实发
- 识别失败行数
- 无法匹配员工数
- 重复员工或重复账号

验收标准：

- 文件上传后，在发布前能看见解析结果。
- 字段缺失时，不能进入“发布并通知”。

## 工作线 B：发布、通知与员工查看安全

### B1. 发布前确认摘要

点击“发布并通知”前弹出确认摘要：

- 月份
- 源文件名 / 导入批次
- 薪资条数量
- 实发合计
- 企业微信可通知人数
- 系统内查看人数
- 不发薪资 / 不发企业微信人数
- 差异未处理人数
- 操作人

必须勾选：

- `我已核对原始薪资表`
- `我已确认发送名单和不发送名单`

验收标准：

- 未处理差异时不能发布。
- 未勾选确认项时不能发布。
- 发布前能看到“会发给谁”和“不会发给谁”。

### B2. 发布状态拆分

当前流程是先同步薪资条，再发企业微信通知。建议状态拆分：

- `salary_published`: 薪资条已发布
- `wecom_notify_status`: 企业微信通知状态
- `employee_visible`: 员工端是否可见

验收标准：

- 企业微信发送失败不应误导为薪资条未发布。
- 薪资已发布但通知失败时，页面能提示“员工可在系统内查看，企业微信待补发”。

### B3. 发布批次 ID

增加 `publishBatchId` 或等价批次号，用于串联：

- 导入批次
- 草稿批次
- 正式薪资条
- 企业微信通知记录
- 操作日志

验收标准：

- 任一员工薪资条可以追溯到哪一次上传和哪一次发布。
- 通知记录可以准确关联到一次发布。

### B4. 员工本人查看校验

员工本人薪资条应优先按明确身份字段匹配：

- `teacherId`
- `userId`
- `wecomUserId`
- `loginAccount`

姓名归一化只能作为兜底，不能作为主要授权依据。

验收标准：

- 同名人员不会互相看到薪资条。
- 企业微信账号变更后，有明确迁移或映射规则。

## 工作线 C：后端、权限、测试与运维

### C1. 后端查询优化

当前 `GET /me/salary-slips` 会读取所有薪资条后在内存中过滤。应改为基于候选身份字段构造数据库查询。

验收标准：

- 数据库层完成过滤。
- 不需要读取全量薪资条。
- 保持月份倒序和同步时间倒序。

### C2. 权限收紧

薪资维护权限建议只允许：

- `SUPER_ADMIN`
- `ADMIN`
- `FINANCE`
- 显式权限 `action.payroll.publish`
- 必要时保留 `action.management.member.update`，但建议拆出薪资专用权限。

移除或降低基于姓名、部门、角色文本正则的放行逻辑。

验收标准：

- 非财务账号不能靠部门或名字文本命中进入薪资维护。
- 权限失败时返回明确错误。

### C3. 同步接口返回更多结果

`POST /salary-slips/sync` 不应只返回 `{ ok: true }`，建议返回：

- `createdCount`
- `updatedCount`
- `skippedCount`
- `teacherIds`
- `publishBatchId`
- `warnings`

验收标准：

- 前端能展示“已同步 N 条、覆盖 N 条、跳过 N 条”。
- 出现重复人员或异常金额时能回显。

### C4. 通知记录保留策略

当前通知记录只保留最近 60 条。薪资审计建议：

- 至少按月份长期保留。
- 支持按月导出。
- 保留发送失败、跳过、补发记录。

验收标准：

- 任意月份薪资发送记录可查询。
- 不因最近记录过多导致旧月份记录丢失。

### C5. 自动化回归

新增端到端或集成回归：

1. 上传 CSV 薪资表。
2. 上传 XLSX 薪资表。
3. 薪资表字段缺失时被阻断。
4. `.xls` 提示不能预览但可进入复核。
5. 导入后返回 `/payroll/batch`。
6. 差异未处理时不能发布。
7. 发布成功后调用 `salary-slips/sync`。
8. 企业微信可发人员进入通知名单。
9. 合作老师 / 无企微账号人员不发企业微信。
10. 员工本人只能看到自己的薪资条。

验收标准：

- 每次构建都能验证“上传入口存在”。
- 每次构建都能验证“发布前必须核对”。
- 每次构建都能验证“本人查看隔离”。

### C6. 本地测试环境

当前仍无法完整前端联调，原因包括：

- Docker 不可用。
- 本机 MySQL 后端演练和生产 schema migration 已完成，但若后续要求 Docker compose 标准环境，仍需补 Docker。
- 静态前端登录接口无法闭环。

建议补齐：

- mock API 模式，用于前端薪资流程自测。
- 一键测试脚本，至少覆盖薪资上传、发布、本人查看。
- 本地环境检查脚本，启动前提示数据库、Prisma、API 状态。

验收标准：

- 没有真实数据库时，也能用 mock 数据走完整 UI 流程。
- 有数据库时，可以一键跑薪资联调回归。

## 推荐实施顺序

1. 先定位可维护前端源码，确认不能直接改压缩发布包。
2. 完成 P0 前端入口和深链返回。
3. 完成 P0 发布前确认摘要。
4. 完成 P1 后端查询优化和权限收紧。
5. 补齐回归测试。
6. 再处理 P2 审计保留和本地环境优化。

## 暂不建议做的事

- 不建议直接修改 `apps/web/public/employee-frontend/releases/20260616090241` 里的压缩 JS。
- 不建议在没有数据库和企业微信 mock 的情况下做真实发布测试。
- 不建议只加一个“去导入中心”按钮就算完成，因为真实问题是上传、返回、核对、发布的闭环不顺。

## 完成定义

该优化完成需满足：

- 薪资批量页有直接“上传薪资表”入口。
- 导入中心可由薪资页带参进入，自动选择薪资表和月份。
- 上传成功后可回到对应月份核对。
- 发布前必须完成原表核对和发送名单确认。
- 员工本人只能查看自己的薪资条。
- 后端权限不依赖文本正则。
- 自动化测试覆盖上传入口、发布阻断、通知名单、本人查看。
