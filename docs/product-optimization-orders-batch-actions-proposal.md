# 订单中心优化方案：批量动作

## 状态

- 当前状态：`正式批量动作 V1 已接入`
- 对应主线文档：
  - `docs/product-optimization-master-plan.md`
- 当前正式页网址：
  - `http://127.0.0.1:3202/orders`

## 当前问题

- 订单工作台已经把 `待收款 / 待发货 / 待结算` 分成泳道，这是对的。
- 但当前主工作台仍以单笔查看和跳转为主，还不能真正批量清队列。
- 团队在高频处理订单时，还是要反复进入：
  - 收款页
  - 发货页
  - 结算页
- 这让订单中心更像导航页，而不是处理台。

## 代码现状判断

- 当前前端主页面：
  - `apps/web/components/orders/OrdersWorkbench.tsx`
- 当前可用接口：
  - 批量可复用潜力最高：
    - `POST /orders/:id/payments`
    - `PATCH /orders/:id`
  - 当前复杂度较高、不适合第一版直接批量化：
    - `POST /orders/:id/shipments`
    - `POST /orders/channel-settlements`
- 原因：
  - 发货需要每张单的明细数量
  - 结算需要订单行与渠道结算项映射
  - 这两类如果直接做批量，很容易变成高风险半成品

## 建议的第一版方案

### 1. 保留当前工作台结构，不重做整页

- 保留：
  - 顶部履约信号
  - 中部三条泳道
  - 右侧 Inspector
- 第一版只补批量动作，不改整体信息架构。

### 2. `待收款` 先做真正批量动作

- 支持：
  - 勾选多张待收款订单
  - 全选当前泳道
  - 清空已选
  - 批量登记到账
- 第一版的规则建议：
  - 默认按每张单“剩余应收金额”全额登记
  - 统一填写：
    - 收款方式
    - 收款账户
    - 收款时间
    - 备注
- 这样可以直接沿用现有 `POST /orders/:id/payments` 逐条提交。

### 3. `待发货` 先做前置资料批量补齐

- 第一版不直接批量创建发货记录。
- 先支持批量补这些字段：
  - 出货仓
  - 收货人
  - 联系电话
  - 收货地址
- 这些字段都可沿用现有 `PATCH /orders/:id`。
- 补齐后，团队再进入发货页或订单详情创建正式发货记录。

### 4. `待结算` 第一版先不做真正批量创建

- 先保留当前单笔跳转到结算页的方式。
- 原因：
  - 结算依赖订单行、渠道商和利润明细
  - 如果第一版强做批量，很容易造成结算错误

### 5. 批量提交流程统一

- 页面反馈：
  - 已选数量
  - 处理中 x/y
  - 成功数
  - 失败数
  - 失败项保留重试
- 风险控制：
  - 收款与资料补齐都沿用现有单笔接口逐条提交
  - 第一版不新增后端批量 API

## 我建议先不做的内容

- 不做批量创建发货记录
- 不做批量创建渠道结算单
- 不做跨泳道混合批量处理
- 不做批量取消订单 / 批量确认订单

## 这样安排的原因

- 订单中心最应该先解决的是“能不能快速清高频动作”。
- 收款登记和发货前置资料补齐，都是高频且结构相对稳定的动作。
- 真正的发货创建和渠道结算创建，依赖明细太多，不适合作为第一版批量动作。

## 确认后准备实施的内容

- `待收款` 批量登记到账
- `待发货` 批量补仓库 / 收货资料
- 批量模式、勾选、全选、清空、提交反馈
- 文档同步回写
